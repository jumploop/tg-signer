第四轮修复（连接生命周期收敛）附带发现转正

data.sqlite3 每次读写都漏关连接

tg_signer/sign_record_store.py · 7 处 with self._connect() as conn:

sqlite3.Connection 的上下文管理器只提交/回滚事务，不关闭连接。7 处调用点都依赖它收尾， 于是连接只能等 gc 兜底才释放：实测 30 次 upsert_record() 后仍有 30 个连接存活， gc.collect() 才归零。单次调用看不出问题，多账号并发时会同时压着大量已打开的库与 WAL/-shm 句柄。

# 修复前：7 处都是这个写法 with self._connect() as conn: self._upsert_records(conn, ...) conn.commit() # 只 commit，连接留给 gc
# 修复后：事务 + 关闭收敛到唯一入口 with self._connection() as conn: ... # _connection() 内 finally: conn.close()
@contextlib.contextmanager
def _connection(self) -> Iterator[sqlite3.Connection]:
    conn = self._connect()
    try:
        with conn:          # 保留原先的提交/回滚语义
            yield conn
    finally:
        conn.close()        # 补上原先缺失的关闭

_connect() 本身不改变（仍返回裸连接）： test_connect_enables_wal_and_busy_timeout 直接把它当上下文管理器用并断言 journal_mode / busy_timeout，改签名会破坏该契约。 仓库内 sqlite3.connect 只此一处，因此仍走「收敛到唯一入口」。

本轮三条关键实现说明容易被改错

P2-8 的护栏是启发式，不是沙箱

utils.py · safe_regex_search

CPython 的 re 在灾难性回溯期间不释放 GIL，线程超时也打不断它， 真正的「超时中断」必须引入 regex 等第三方库——本轮不新增依赖， 因此改为「长度上限 + star height ≥ 2 形状检查」。

判别性实证：朴素 re.search(r"(a+)+$", "a"*24 + "!") 需 1.98s，新护栏 0.0000s 抛 ValueError； 6 个危险 pattern 全部命中，11 个常见 pattern 零误报。

P2-17 必须同时传两个参数

webui/runner.py · build_command

只传 --log-dir 时 CLI 的 --log-file 仍取相对默认值， 子进程会在自己的 cwd 下另建 logs/ —— 这正是原缺陷的成因。 所以修复必须显式给出 --log-file 的绝对路径，指向每子进程独立目录。

同理 P2-4 只改传递通道：TG_PROXY 是 CLI 已有的 envvar， 改 runner.py 即可，cli/signer.py 无需改动。

环境限制实证与代码无关，结论可直接引用

本沙箱的 WAL 不可用（-shm 共享内存映射被拦截）

tests/test_sign_record_store.py · test_concurrent_upserts_never_raise_database_is_locked[cold] 与 [initialized]

这两条用例在本沙箱都必然失败（SQLITE_READONLY: attempt to write a readonly database）。 逐层排除过程如下，每一项都是实跑结果：

实验结果
8 线程冷启动（现状）7/8 失败，错误码 SQLITE_READONLY(8)，失败点是 executemany
PRAGMA journal_mode=WAL 改为「重试到真的切成功」仍 7/8 失败；且探针显示 pragma_err 全为空、所有连接看到的 mode 都是 wal
表与 WAL 都预热，只做 INSERT仍 2/8 失败
整个 bootstrap + 写一起重试 6 次仍 6/8 失败（不是瞬时错误，重试无效）
并发数 1 / 2 / 4 / 80 / 1 / 3 / 7 失败 —— 恰好 N−1，永远只有一个赢家
换目录（系统 temp / 仓库内 / D 盘）三个位置行为完全一致
换 journal_modeDELETE 2、4 并发 0 失败；TRUNCATE 0 失败；只有 WAL 坏
第四轮：改为每次显式关闭连接（各 3 次）旧 / 新实现均 7/8 失败 —— 排除「连接泄漏」这条路

结论：WAL 要求多连接共享同一份 -shm，被拦截后 SQLite 对第二个及以后的连接直接返回 SQLITE_READONLY；同一环境下 Path.symlink_to() 也会不报错地退化成普通文件 （lstat 0o100666、无重解析点），说明该拦截层会同时影响文件系统语义。

因此没有把 journal_mode 改成 DELETE：WAL 是正确处理（单写多读、跨进程友好）， 为迁就本沙箱改掉会降低真实部署的并发能力。这两条用例在正常机器上应当通过。 （第四轮确实动过 sign_record_store.py，但只为补上连接关闭，与 journal_mode 无关。）

容易改回去的实现细节反直觉

只加 timeout 修不好 SQLite 冷启动

sign_record_store.py · _connect

多连接同时从 delete 切向 WAL 时，SQLite 对失败者直接返回 SQLITE_BUSY 且不调用 busy handler， 只加 timeout 实测仍有 2/8 线程失败。真正的根因是 rollback-journal 模式下 COMMIT 需要 RESERVED→EXCLUSIVE 升级、被其他读者挡住会立刻报 locked —— WAL 才是修复本身，切换过程还需容错。

测试写死的超时是环境相关的

tests/test_main_entry.py · timeout=30

本机 import pyrogram 需约 13s，CLI 冷启动 15~20s，--help 可达 54s。 「启动应在 30s 内完成」这条隐含假设在慢机器 / 并发跑测下不成立。若要让测试跨环境稳健， 应按实测启动耗时自适应，而不是把超时直接调大掩盖问题。

Path.symlink_to() 可能静默降级

tests/test_utils.py · 软链逃逸守卫

Windows 上缺 SeCreateSymbolicLinkPrivilege 或被安全软件拦截时， symlink_to() 可能不抛异常而退化成一个普通文件（lstat 0o100666、无重解析点）。 只写 except OSError: pytest.skip 拦不住，必须在创建后补 if not link.is_symlink(): pytest.skip(...)。

打桩 os.name 会连带改变 pathlib 的行为

tests/test_utils.py · restrict_file_permissions

monkeypatch.setattr(os, "name", "posix") 改的是全局 os 模块属性， 此时 pathlib.Path() 会构造 PosixPath，与 tmp_path 的 WindowsPath 不相等，断言会假失败。测试里不要在该窗口内重新包装 Path。

P2-18　爆破防护形同虚设：受保护端点不记账 P2 中高

tg_signer/webui/server.py:151-165（require_auth） · 对比 :603-620（auth_login）

require_auth 是全部受保护端点的依赖，它会检查锁定状态， 但自己从不记账 —— record_auth_failure() 只在 /api/auth/login 里被调用。 于是攻击者只要不走登录端点、改用任意受保护端点携带猜测的 Bearer，就完全绕开限流。

def require_auth(authorization = Header(default=None)) -> None:
    if not expected:
        return
    with _auth_storage_lock:
        if auth_helpers.is_auth_locked(_auth_storage):   # 只看，不记账
            raise HTTPException(429, ...)
        if authorization != f"Bearer {expected}":        # 猜错也只返回 401
            raise _challenge()                           # ← 没有 record_auth_failure
=== 路径 1：正经走 /api/auth/login 爆破 === 状态码序列: [200,200,200,200,200,429,429] ← 第 6 次被锁 锁定状态: {'auth_failed_attempts': 0, 'auth_locked_until': 25908.7}
=== 路径 2：绕开登录端点，直接打受保护端点 === 状态码序列: [401 × 30] ← 30 次全是 401 出现 429（被锁）: False 失败计数存储: {}（空 = 从未记账）

影响：授权码是唯一的认证凭据，猜中即等于完整控制（账号登录/注销、读日志、 拉起任务、改配置、读 LLM 密钥掩码）。没有限流意味着可无限次在线猜测。

P2-19　锁定可被用于 DoS：全局单例 + 「先锁后验」 P2 中高

tg_signer/webui/server.py:157-165 · 计数存储 _auth_storage（server.py:36）是模块级单个 dict

两个独立问题叠在一起：① 全局单例 —— 任何人触发锁定，锁的是所有人； ② 先锁后验 —— auth_login 先判 is_auth_locked() 再比对授权码， 所以锁定期内正确的授权码同样被拒。

=== 攻击者用 5 次错误登录锁死服务 === 第 5 次后锁定剩余: 60.0 秒 === 合法用户拿着正确授权码，此刻也被拒 === 正确码登录 -> 429 {'detail': '尝试次数过多，请 60 秒后再试'} 正确 Bearer /api/state -> 429 === 持正确令牌的合法用户，整个 API 面被锁 60s === /api/accounts -> 429 /api/logs/files -> 429 /api/run -> 429

影响：未认证攻击者每 60 秒发 5 个 /api/auth/login 请求（无需知道授权码）， 即可让 WebUI 对所有人永久不可用。这比不做限流更糟：不做限流只是防不住爆破， 而这个实现额外提供了一个廉价的远程拒绝服务原语。

P2-18 与 P2-19 是同一处设计的两面：叠加后这个「防护」既不挡攻击者、又能被攻击者用来打别人。

修复方向建议（P2-18 / P2-19，本轮未改代码） 待决策

core idea：把「先锁后验」换成「先验后锁」

正确修法不是「把 record_auth_failure 挪进 require_auth」—— 那样会让携带过期令牌的正常前端（每次请求都带 Bearer）快速把自己锁死，把 P2-19 的 DoS 从「攻击者主动触发」变成「日常自伤」。建议先验后锁：

# 思路：先判凭据，凭据正确直接放行（不受锁定影响）；错误才记账并触发限流。
with _auth_storage_lock:
    if not secrets.compare_digest(authorization or "", f"Bearer {expected}"):
        auth_helpers.record_auth_failure(_auth_storage)   # 记账移到错误分支
        if auth_helpers.is_auth_locked(_auth_storage):
            raise HTTPException(429, ...)
        raise _challenge()
# 凭据正确 → 直接放行，锁定期内合法用户不受影响

要点：① 记账发生在任何携带错误凭据的请求上（堵住 P2-18 的绕过）； ② 正确的凭据跳过锁定检查（消除 P2-19 对合法用户的 DoS）； ③ 用 secrets.compare_digest 顺带解决 P3-9。auth_login 同样按「先比后记」调整即可。
